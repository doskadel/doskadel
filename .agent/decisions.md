## 2026-10-04 — Финальный статус у повторяющихся (пауза/закрытие серии)

**Контекст:** сейчас расхождение - dueItems (agenda) учитывает финальный статус (isFinal:false), а taskDueSummary/computeOccurrences (список/календарь/dashboard) НЕТ. Повторяющаяся в финале продолжает давать вхождения.

**Решение (арбитр):** финальный статус = серия приостановлена/закрыта, будущих вхождений/просрочек/счётчиков быть не должно. Единый источник - computeOccurrences, фильтр isFinal в нём (не в потребителях).

**Механика:**
- Task.activeSince (дата последнего возврата в нефинальный статус, дефолт createdAt). computeOccurrences считает вхождения только если статус нефинальный и только с max(activeSince, начало по правилу).
- Смена финальный->нефинальный: activeSince = now (в зоне задачи); пропущенное за период финала не восстанавливается и не missed.
- Для финальных: nextOccurrenceDueAt=null, счётчики 0, будущие в календаре не рисуются.

**Причина финала (closedReason):** completed|split|manual. Финал по closedReason не возвращается пользователем; ручной перевод в финал (без closedReason) = пауза/закрытие, возвращается. Возврат задачи с closedReason (completed/split) в активный запрещён (или сброс closedReason осознанно с подтверждением); split-старую не возвращать никогда.

**История:** done/skipped/missed сохраняются; авто-missed пропускает финальные; материализация pending/пуши для финальных не создавать.

**Тесты:** финальная -> 0 в summary/календаре/dashboard/agenda; возврат -> вхождения только от activeSince (без хвоста); история цела; completed/split не возвращаются; авто-missed не трогает финальные; смена статуса несколько раз. Миграция: activeSince=createdAt (dry-run).

**Порядок:** после F1e.

## 2026-10-04 — Сессии: сроки и автовылет (решение арбитра)

**Контекст:** access в памяти, refresh в httpOnly cookie, rotation+reuse-detection, Origin. Refresh TTL 30д фикс, скользящего продления и абсолютного максимума нет.

**Решение (сроки):**
- Access 15 мин (есть).
- Refresh скользящий: каждый refresh -> новый токен с idle-TTL 30 дней (заходишь раз в месяц -> пароль не спрашивают).
- Абсолютный максимум 90 дней от логина (familyCreatedAt в семье), для личного 180.
- 'Помни меня': вкл -> persistent cookie (Max-Age=idle-TTL); выкл -> session cookie, idle 24ч. По умолчанию вкл.
- Гонка вкладок: grace 10-30с (повтор ротированного токена не отзывает семью) + single-flight refresh на клиенте (BroadcastChannel).
- Инвалидация: смена пароля отзывает все семьи кроме текущей; forgot-reset — все. В 'Безопасности': список сессий + 'Выйти везде'.
- Cookie: httpOnly, Secure, SameSite=Lax, Path /auth (на разных сайтах — None+CORS credentials).
- Холодный старт PWA: сразу refresh, скелетон (не логин).
- TTL в env, UTC.

**Тесты:** скользящее двигает idle; абсолют не продлевается; grace не отзывает; реальный reuse после grace отзывает; 'не помнить' -> session cookie; смена пароля отзывает чужие семьи.

**Статус:** запланировано (S-сессии). Текущая схема рабочая, доработка не срочная.

## 2026-10-04 — F1c: повторяемость как параметр задачи (итоговый ADR)

**Решение:** одна сущность Task, recurrence = необязательное правило (freq/interval/byWeekday/byMonthDay/time/until/count/tz); нет recurrence = разовая. Occurrence = исключения и история (originalDate ключ, unique {taskId,originalDate}; status pending|done|skipped|missed; dueAt при переносе; completedAt/By). Будущие вхождения считаются на лету (computeOccurrences, горизонт 12 мес); запись Occurrence — при действии (done/skip/move) или материализации под пуш.
**Разделение серии (scope following):** старая Task.until = перед orig + closedReason=split; новая Task (копия, seriesId, prevTaskId, пересчёт count); исключения >= orig переносятся (защита unique, не теряем факт); компенсация при сбое.
**tz:** recurrence.tz = IANA, обязателен (валидация), из клиента; расчёты в зоне пользователя (X-Timezone); DEFAULT_TZ только в миграции.
**Пуши at-most-once:** флаг ставится до отправки (compare-and-set), при ошибке снимается (unmarkNotified), лимит попыток 3 (notificationsSent.*Attempts).
**Авто-missed:** старые просроченные pending -> missed (utils/autoMissed, dry-run), последнее оставляем.
**Убрано:** confirm/unconfirm API, confirmedAt, OccurrenceConfirmModal (заменено /action + историей).
**Отложено (F1e):** подпись 'Повторять'+сводка, 'Начало', статус вхождения в карточке, aria-label, автотест отказа confirm.
**Merge:** 0a199c5 (--no-ff).

## 2026-10-04 — ADR: пуш at-most-once (F1c этап 2)

**Решение:** пуш не слать дважды (параллельные job). Флаг ставится ДО отправки (compare-and-set, markNotified). При ошибке отправки или sent=0 флаг снимается (unmarkNotified) для повтора. Ограничение попыток: 3 (notificationsSent.<type>Attempts), при превышении — флаг остаётся, ошибка логируется (пуш потерян, не спамим). Итог: at-most-once с ретраями до 3.

**Floor в computeOccurrences:** параметр ctx.floorDays (дефолт 90 для job). История вхождений читает done/skipped/missed из БД напрямую (не через compute). Календарь на прошлые месяцы — при необходимости передаёт больший floor.

## 2026-10-04 — ADR: tz в recurrence (F1c)

**Решение:** recurrence.tz = IANA-зона (напр. Europe/Moscow). Вхождения считаются в этой зоне, в UTC переводятся при расчёте (учёт летнего времени). originalDate = datetime (для мигрированных = старый dueAt).

**Дефолт tz:** временно Europe/Moscow (миграция, DEFAULT_TZ из env). Триггер/план: tz брать из настройки пользователя/workspace (добавить в UI настроек — TODO). Дефолт сменный, решение за оператором.

## 2026-10-04 — ADR: повторяемость как параметр задачи, исключения через Occurrence (F1c)

**Контекст:** сейчас повторяемость через type/weekly/monthly + заранее создаваемые Occurrence (горизонт 7 дней). Ограничения: нет interval/until/count/tz, нельзя переносить отдельное вхождение, нет пропуска/авто-missed, доска по статусу задачи, а не вхождения.

**Решение:** одна сущность Task; recurrence = необязательное правило (freq, interval, byWeekday, until|count, tz). Нет recurrence = разовая. Occurrence = исключения и история (taskId, workspaceId, originalDate — ключ, unique {taskId, originalDate}; dueAt — если перенесено; status pending|done|skipped|missed; completedAt/completedBy). Будущие даты считаются из правила на лету (горизонт 12 мес). Запись Occurrence создаётся ТОЛЬКО при действии (done/skip/move); регенерация их не затирает. Разовые: поведение и dueDate не меняются. Единая абстракция сроков (dueItems/taskDueSummary) остаётся; источники дат: dueDate и recurrence+Occurrence.

**Семантика:** выполняется вхождение, не задача. После done сразу виден следующий срок. Конец по until/count: после последнего закрытого вхождения Task.status = завершена. Бессрочная: ручное 'Завершить повторение' с подтверждением. Просрочки: только последнее просроченное; старые авто-missed (в истории). 'Накапливать' — позже.

**UI:** доска — одна карточка, колонка по статусу ТЕКУЩЕГО вхождения; после 'Выполнено' возврат в 'В ожидании' с новой датой, в 'Готово' не копятся. Календарь: done приглушено с галочкой, skipped зачёркнуто. Правка/перенос: диалог 'Только это / Это и следующие / Все'. DnD повторяющихся включается (снять запрет F1b). История — вкладка в карточке. Одна форма задачи с переключателем 'Повторять'.

**Отвергнутые альтернативы:** (а) отдельная сущность 'серия' (Series) — лишний слой, дублирование с Task; (б) заранее материализовать все вхождения — тяжело, конфликт с исключениями; (в) хранить только правило без Occurrence — нельзя перенос/пропуск/историю; (г) oставить как есть — не решает перенос вхождения и завершение серии.

## 2026-10-04 — Фундамент workspace: решение по идентификаторам

**Контекст:** план фундамента (workspaces/can/workspaceId) предполагал п.7 — переход на UUID/ULID. Аудит (AUDIT_FOUNDATION.md) показал: проект на MongoDB, ObjectId.

**Решение (арбитр, Claude):** ObjectId ОСТАВЛЯЕМ, на UUID/ULID не переходим.
- Безопасность держится на авторизации (404 на чужой id, фильтр по workspaceId), а не на неугадываемости id.
- ObjectId глобально уникальны, переносимы между инсталляциями.
- Миграция всех ref+индексов — риск без выигрыша.
- Триггер возврата: публичные ссылки → отдельное поле publicId (nanoid), не замена _id.

**Поправки к плану под Mongo:**
- workspaceId: ObjectId, ref Workspace, required, index. Составные индексы {workspaceId, ...}; userId-индексы заменять после бэкфилла.
- Бэкфилл — идемпотентный скрипт (dry-run, счётчики): на каждого User Workspace + Membership(owner), затем updateMany userId -> workspaceId, createdBy=userId. Перед запуском mongodump.
- userId в сущностях остаётся как createdBy (переименование отложено, API не ломаем).
- can() + репозиторий: сначала Task/Occurrence, затем Article/Status, пачками с тестами. Agenda job'ы: workspaceId из записи.
- Из отложенного в этом шаге делать только assignee_id (nullable) и deletedAt; soft-delete/настройки/auth_identities — в decisions с триггером.

**Старт шага 2:** только по явному сигналу оператора.

## 2026-10-03 — DnD в календаре (F1b): только разовые задачи

**Контекст:** F1b — перетаскивание дедлайна в календаре. Разовые хранят Task.dueDate, повторяющиеся — серию Occurrence.dueAt. Арбитр (Claude) рассмотрел 4 варианта для повторяющихся.

**Следствия:**

- Защита **на сервере**: updateTask при попытке сменить dueDate у повторяющейся должен отказывать (не только фронт).
- **Отложено в F1c:** перенос конкретного вхождения (модель исключений overridden/exceptionOf — иначе регенерация серии затрёт ручной сдвиг) + диалог «Только это / Вся серия». Причина отложения: нет модели исключений.

## 2026-10-03 — Решения арбитра (Claude) по проекту

**Контекст:** ядро закрыто, проект DoskaDel (зрелый MVP) требует UX/дизайн/доработок. Вопросы заданы Клоду, получены ответы.

### Защита несохранённых данных (2026-10-03)
**Решение:** выход из формы создания/редактирования без сохранения (X/фон/Esc/Назад/смена экрана) — confirm-диалог, только при реальных изменениях (снимок + isDirty). Покрыто: ProfileModal, Dashboard, StatusManager, TaskModal/ArticleModal (хуки), TaskDetail/ArticleDetail, SearchModal. Правило в RULES.md.

### Порядок работ
1. **Дизайн-система + темы** (фундамент визуала).
2. **Вход/авторизация** — поднять ВЫШЕ (первое впечатление, конверсия, дёшево, строится на дизайн-системе).
3. **Календарь** (самый дорогой — резать скоуп: месяц/неделя/день, drag&drop, без внешних календарей).
4. **Профиль** (мелкий, между делом).
5. **Бот** — последним.
Голос: бесплатно (Web Speech API на клиенте, в бот уходит текст), платные STT не подключать.

### Позиционирование (решение оператора + совет Клода)
- Ядро: **личное + малые команды**, без мультитенантности/ролей/биллинга сейчас.
- Монетизация: freemium для личного; платное — совместная работа малых команд, но только после подтверждения спроса 5-10 реальных пользователей.

### workspaceId — через единый слой доступа (ответ Q5)
- **Модели пока не менять.** Поле `workspaceId` в User (personal workspace) + коллекция Workspace {_id, ownerId}.
- **Ключевое:** все запросы к данным пропустить через **единый слой** (репозиторий/хелпер), где сейчас фильтр `userId`. Тогда переход на workspaceId = правка в одном месте + скрипт миграции, а не по всему коду.
- Вариант Б (workspaceId во все модели сейчас) — преждевременен.

### Auth: cookie-схема (ответ Q4)
- **Один домен + reverse-proxy** (nginx/Caddy в Docker): `/` -> фронт, `/api` -> бэк. Cookie first-party, CORS не нужен.
- Cookie: **httpOnly, Secure, SameSite=Lax** (Strict допустим), `Path=/api/auth/refresh`.
- **В dev так же:** прокси CRA/Vite `/api` на бэк (порты 3000/5000 не мешают).
- **SameSite=None — НЕ брать** (усложняет CORS, ослабляет CSRF).
- **localStorage для refresh — НЕЛЬЗЯ** (XSS крадёт на 30 дней; reuse-detection не лечит).
- **Проверка Origin на refresh/logout** — дешёвая CSRF-защита.
- Access (15м) — держать **в памяти JS**, после перезагрузки получать заново через refresh.

### Бот-ассистент (ответ Q6)
- **LLM в проде — на сервере**, не на клиенте (ключ нельзя отдавать в SPA). Дев-инструменты (DeepSeek-чат, userscript) к продукту не относятся.
- Провайдер **сменный через один адаптер** и env-ключ; rate limit на пользователя. Бесплатный tier (Ollama Cloud/Groq/Gemini) для старта ок, без SLA. Локальная Ollama (8 ГБ) — только для дева.
- **Изменения данных:** LLM НЕ пишет в БД, а возвращает структурированное **намерение** (search_tasks, update_task с id и полями). Сервер валидирует схемой, проверяет владельца (`userId` из токена, НЕ из ответа LLM); для изменений/удалений — **превью-diff с подтверждением**; поиск/чтение без подтверждения.
- **Prompt injection:** текст задач/статей в промпте — недоверенный; действия только по запросу пользователя, не по инструкциям из данных.
- **RAG на бэке:** для сотен-тысяч записей хватит **Mongo text index**, эмбеддинги не нужны на старте. Фильтр по userId/workspaceId — всегда до подачи в LLM.
